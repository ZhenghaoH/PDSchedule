# 项目代码结构说明

PDSchedule 当前专注于 Prefill/Decode 动态配对、分层调度、KV Cache 传输和运行状态观测。主要目录如下：

```text
.
├── config/                     # Controller、P/D Gateway、P/D Instance 与网络默认配置
├── connectors/                 # Connector 协议、注册表、会话管理及 NIXL/LMCache Adapter
├── coord/                      # Controller、Gateway、Instance 之间的注册与上报
├── core/
│   ├── commands/               # 控制台命令实现
│   ├── consoles/               # Controller 与 Gateway 交互式控制台
│   ├── handlers/               # HTTP 请求处理、代理、注册、心跳和 Connector 会话
│   ├── lifespans/              # 各服务启动与关闭生命周期
│   ├── routers/                # FastAPI 路由
│   └── schemas/                # 请求和命令数据结构
├── doc/                        # 架构、部署与 PD 分离说明
├── entrypoints/                # Controller、P/D Gateway、P/D Instance 等启动入口
├── examples/                   # 客户端和 NIXL 部署示例
├── instance/
│   ├── perception/             # vLLM、GPU、吞吐和负载指标采集
│   └── simulator/              # Instance 响应模拟
├── profile/                    # TTFT、TPOT、吞吐建模工具与 Controller 运行时模型
├── proxy/                      # HTTP 转发、请求批处理和 Prefill 调度执行闭环
├── scheduler/
│   ├── controller/             # 全局策略管理、资源快照与 P/D 池调度策略
│   └── gateway/                # P/D Gateway 池内实例调度策略
├── store/
│   ├── controller/             # P/D 资源池与网络状态
│   ├── gateway/                # 实例、预约负载、Connector 与策略状态
│   └── instance/               # Instance Proxy 运行配置
├── templates/                  # Controller 请求状态页面
├── test/                       # 主系统单元测试与集成测试
└── utils/                      # 地址、网络、PCIe、Tokenizer 和日志工具
```

## 主请求链路

1. 客户端向 Controller 的 `/v1/chat/completions` 或 `/v1/completions` 发送请求。
2. Controller 构造 `BaseRequest`，先过滤 Connector 不兼容的 P/D Pool；单个兼容组合直接选择，多 Gateway 时使用当前全局调度策略。
3. Prefill Gateway 使用当前 Prefill 策略选择在线 P Instance，并执行 Prefill。
4. Prefill 完成后，P Gateway 通过通用 `connector_context` 将 NIXL/LMCache 所需上下文发送到 Decode Gateway。
5. Decode Gateway 使用当前 Decode 策略选择在线 D Instance，完成流式 Decode。
6. Gateway 和 Instance 持续上报请求负载、GPU、显存、网络及时间观测数据。

## Controller 全局调度器

`scheduler/controller/` 按职责分为：

```text
scheduler/controller/
├── global_scheduler.py        # 请求转换、单 P/单 D 快速路径和结果编排
├── manager.py                 # 策略注册、查询、切换和统一执行
├── resource_state.py          # 版本化 P/D Pool 与 Network 原子快照
├── strategy.py                # 策略上下文、结果和统一协议
└── strategies/
    ├── demand_aware.py
    ├── least_load.py
    └── round_robin.py
```

全局调度器仅暴露 `demand_aware`、`least_load` 和 `round_robin` 三项策略，
默认使用 `demand_aware`。单 P/单 D 时直接选择唯一组合，不进入具体策略。
三个策略都只能从 `ResourceSnapshot.compatible_pairs` 选择候选。

Pool 注册、负载心跳、网络更新或注销成功后，Controller 会立即发布新的资源快照，
使下一次调度直接读取新版本。后台任务每 1 秒进行一次状态核对，只负责资源超时
失活和漏通知兜底；Pool 和 Network 继续分别沿用 3000 秒和 60 秒的活跃超时。

## 关键扩展位置

- 新增 Controller 策略：在 `scheduler/controller/strategies/` 中创建与策略同名的
  文件，实现 `strategy.py` 的统一接口，并注册到 `manager.py`
- 新增 Prefill Gateway 策略：在 `scheduler/gateway/prefill/` 中创建与策略同名的文件，实现 `strategy.py` 的统一接口，并注册到 `manager.py`
- 新增 Decode Gateway 策略：在 `scheduler/gateway/decode/` 按策略名增加实现文件，并注册到 `manager.py`
- 调整请求协议：`core/schemas/request.py`
- 新增或调整 Connector：`connectors/`（首期注册表仅允许 `nixl` 与 `lmcache`）
- 调整 P/D 转发链路：`core/handlers/gateway/prefill/proxy.py`、`core/handlers/gateway/decode/proxy.py`
- 调整实例注册和指标：`core/handlers/gateway/*/update.py`、`coord/instance/up_store.py`

当前运行时 Connector 仅支持 NIXL 与 LMCache。Redis 和 Mooncake Store 等后端材料
用于说明 LMCache 的共享存储部署，不代表注册了其他 P2P Connector；相关后端仍需
按实际运行时版本验证。
