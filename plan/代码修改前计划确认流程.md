# 代码修改前计划确认流程

## 目的

在任何业务代码、配置代码、脚本或测试代码修改前，先在 `plan/` 目录下创建本次任务专用的 `.md` 修改计划文件，等待用户明确确认后再执行代码变更。修改和验证完成后，经用户确认，将本次任务的有效改动提交并推送到 GitHub 项目 `BJTU-ANT/FlexPD` 的 `PDSchedule` 分支。`PDSchedule` 分支首次创建时，必须以更新且干净的 `origin/p2p-flexpd` 为基线；创建完成后，后续任务默认在 `PDSchedule` 分支修改，并推送到 `origin/PDSchedule`。

## 执行规则

1. 收到具体修改需求后，先阅读相关代码、配置和已有文档，确认影响范围。
2. 在 `plan/` 目录下创建一份本次任务专用的修改计划文件，文件名应能反映修改主题。
3. 修改计划至少包含：
   - 修改目标
   - 拟新增或修改的文件范围
   - 拟采用方案
   - 风险点
   - 验证方式
   - Git 提交范围和建议的提交信息
   - 是否推送到 `origin/PDSchedule`
   - 待用户确认事项
4. 在用户明确确认前，只允许修改计划文件，不修改业务代码、配置代码、脚本或测试代码。
5. 用户确认后，再按照计划执行修改，并在完成后说明实际改动和验证结果。
6. 代码按照计划修改完成并完成验证后，删除本次任务对应的专项修改计划文件。
7. 后续阅读仓库中的文本文件时，默认按 UTF-8 编码读取；如果 PowerShell `Get-Content` 出现中文乱码，应显式使用 `-Encoding UTF8`、先设置终端 UTF-8 输出编码，或使用 Python `Path.read_text(encoding="utf-8")` 读取，避免因控制台编码误判文件内容。
8. 测试文件范围应根据修改风险、现有测试组织和可复用性确定，不得默认每次修改都在 `test/` 目录中新建测试文件：
   - 优先复用或扩展能够覆盖本次行为的现有测试文件。
   - 对文档、注释、简单配置或低风险机械修改，可采用静态检查、既有回归测试或针对性命令验证，不强制新增测试代码。
   - 只有当功能具有独立测试边界、放入现有测试会造成职责混乱，或现有测试无法合理覆盖时，才新增专项测试文件。
   - 修改计划必须说明采用的验证方式及是否需要新增测试文件；若新增，应说明必要性。

## GitHub 提交与推送流程

1. 开始修改前，使用 `git status --short`、`git branch --show-current`、`git branch -vv` 和 `git branch -r` 检查工作区、当前分支、本地与远端分支及其上游关系：
   - 默认工作分支应为 `PDSchedule`。
   - `PDSchedule` 已发布后，上游分支应为 `origin/PDSchedule`。
   - 远程 `origin` 应指向 GitHub 项目 `BJTU-ANT/FlexPD`。
   - 如果存在用户已有的未提交改动，必须识别并保留，不得覆盖、回退或混入本次提交。
   - 如果本地 `PDSchedule` 尚不存在，必须先获取远端最新状态，并确认本地 `p2p-flexpd` 与 `origin/p2p-flexpd` 一致且工作区干净，再经用户明确授权后从该基线创建 `PDSchedule`。
   - 如果远端 `origin/PDSchedule` 已存在而本地尚无该分支，不得从 `p2p-flexpd` 另行创建同名分支；应先检查远端历史，再安全创建跟踪 `origin/PDSchedule` 的本地分支。
   - 分支名区分大小写，必须使用精确名称 `PDSchedule`。
2. 代码修改和验证完成后，先删除本次任务对应的专项修改计划文件，再使用 `git status` 和 `git diff` 核对最终改动，确保提交范围只包含本次任务需要保留的文件。
3. 在提交和推送前，向用户说明：
   - 实际修改内容和验证结果。
   - 拟暂存的文件范围。
   - 建议的提交信息。
   - 目标远程与分支：`origin/PDSchedule`。
4. 只有在用户明确确认提交和推送后，才执行 Git 写操作。不得擅自暂存、提交或推送。
5. 推送前先获取远端最新状态，并确认本地分支可以安全更新：
   - 如果远端包含本地尚未合入的提交，停止推送并说明差异，由用户确认采用合并或变基方案。
   - 不得使用 `--force` 或 `--force-with-lease` 覆盖远端历史，除非用户针对该操作另行明确授权。
   - 如果 GitHub 身份验证失败，应停止流程并提示用户配置或恢复有效凭据，不得绕过认证。
6. 按用户确认的文件范围暂存并复核暂存区差异，创建提交后推送到 `origin/PDSchedule`：
   - 首次发布新分支并建立上游跟踪关系时，执行 `git push -u origin PDSchedule`。
   - 已建立上游跟踪关系后，执行 `git push origin PDSchedule`。
7. 推送完成后，核对本地提交、上游跟踪状态和工作区状态，并向用户报告提交哈希、提交信息、推送目标及最终验证结果。
8. 如果提交或推送失败，不得宣称流程完成；应保留现有改动，说明失败原因和安全的后续处理方式。
